terms:
  DDD: >-
    Domain-Driven Design. A way to describe a service in the words of its
    domain, and to agree on what each of its levels decides.
  ubiquitous language: >-
    One set of words for the whole context: a word has one meaning, and the
    code, the events, the API and the people all spell it the same way.
  bounded context: >-
    The stretch of a system inside which one word has one meaning. Outside it
    the same word may mean something else, and the translation happens at the
    border.
  aggregate: >-
    A piece of state that changes as a whole and by its own rules. The
    transaction boundary: nothing outside can reach past it.
  use case: >-
    One reason the service does something: read, check, change, announce. The
    order of the steps and nothing beyond it.
  adapter: >-
    The translation between the service and what is outside it: a database, a
    queue, somebody else's API. No rules live here, only translation.
  transport: >-
    The edge of the service: how a request arrives and which code answers it.
    No decision about the domain is made here.
steps:
  - id: language
    title: The ubiquitous language
    narration: >-
      The first thing a service pins down is its words. A word inside the
      context has one meaning, and everything spells it the same way: the code,
      the events, the API and the person on the call. The glossary is a file
      next to the code rather than a page in a wiki: a page is edited apart from
      the code, and six months later it lies. The rule is simple — a word that
      is not in the glossary is not in the code either. Name it first, write it
      after.
---

**<span data-term="DDD">DDD</span>** answers that with a single agreement: a
service has levels, and each level decides exactly one thing. The
<span data-term="bounded context">bounded context</span> — what the service
owns and which words it uses for it. The
<span data-term="aggregate">aggregate</span> — which states are possible and
which transition between them is legal. The
<span data-term="use case">use case</span> — in what order that happens and who
it calls to do it. The <span data-term="adapter">adapter</span> — how the same
thing sits in a database and travels over the network. The
<span data-term="transport">transport</span> — which code to answer with. The
agreement is the same for every service, so the next service reads like the
last one, and a known problem gets its known answer: it is immediately clear
which level it lives on and where to put it.
